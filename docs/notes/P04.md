## Para integración (P99)

2. **Sin Homebrew no hay conflicto en el plan.** `Detection` no dice si existe `brew`: los `BrewInstall` fallan al aplicar con «No se ha encontrado Homebrew.». Propuesta: añadir `Detection.brew: bool` y convertir esos pasos en `Conflict`. Cambia el contrato, así que no lo he hecho.
3. **Novedades de `SETUP_VERSION`.** `SetupStatus.news` y `Step::since` existen, pero no hay ningún comando para guardar la versión nueva sin cambiar el escenario (04 §4.8: «al aceptar o al descartar»). Hoy `SETUP_VERSION = 1`, así que nunca hay novedades. Cuando suba, hará falta algo como `setup_ack_news`. El filtro `since > version` lo puede hacer el frontend sobre `plan.steps`.
4. **`brew::apply` no entrega líneas** (no tiene `on_line`). Los pasos `Service` solo emiten Running/Ok/Failed, sin la última línea de brew. Si se quiere, `brew.rs` (P01) puede ganar una variante con `on_line`.

## Decisiones dentro del paquete (sin cambiar el contrato)

- **Funciones públicas añadidas** en `elephant_core::setup`: `plan_measured` (como `plan`, pero con la RAM real de los servicios en marcha mediante `monitor::usage_for`; `plan` sigue siendo pura) y `apply_if_current` (no ejecuta nada si el `id` no coincide y devuelve `Stale`). P09 puede usar las dos.
- **`Plan.id`** es la huella (sha256, 32 hex) de lo que se ejecuta y se explica: escenario, pasos, «ya lo tienes», avisos y conflictos. **No** incluye los totales, porque la RAM medida varía entre llamadas, ni datos irrelevantes de la detección, como un `pid`. Un plan solo queda obsoleto si cambia lo que haría.
- **`setup_apply`** solo acepta el `plan_id` del último `setup_preview` de la sesión (`SetupState` guarda la entrada y el plan). Si no coincide, devuelve un error que pide volver a revisar. Después recalcula el plan y, si ha cambiado, devuelve `Stale` con el nuevo, que pasa a ser el pendiente.
- **`setup.json`** se guarda al terminar `setup_apply` aunque haya fallos (Ajustes ▸ Escenario mostrará las diferencias), pero **no** si se canceló. Después llama a `state::refresh`, porque la app ignora los `stamp` con su propio `pid`. El núcleo hace `stamp::touch("components")` y `("php")` si algún paso terminó bien.
- **`detect(launch_at_login)`** compara `~/.elephant-stack/bin/php` con el selector que hay junto al ejecutable actual (`php-selector` y, en debug, `php`), la misma regla que `sidecar::path`. Así la firma de §5.4 no cambia y vale también para la CLI. Si no encuentra el selector, lo instalado se da por bueno (`Same`).
- **`PathState::AfterHerdMissing`** = no hay línea de Elephant, pero sí la de Herd (el bloque se añadiría después). `Missing` = no hay ninguna de las dos. Las dos dan el mismo aviso.
- **«Tienes Composer de Herd»** se avisa si Herd está instalado (Herd siempre trae `composer`); «de Homebrew», si existe la fórmula `composer`.
- **`ops::install_component("composer")`** → `setup::install_composer`: si falta el selector `php` y se encuentra el empaquetado, lo instala también, porque el envoltorio `bin/composer` lo necesita.
- **Personalizado desde el sistema** (`profile_from_system`) enseña MySQL, PostgreSQL 18, Redis y Mailpit (`WIZARD_SERVICES`), las ramas de las versiones propias y la global actual como `default_php`. Su plan sale vacío (test en los tres Mac sintéticos).
- `download_php` usa la misma maquinaria que `apply` (eventos, log y `stamp`) con un plan de un paso. No se puede cancelar, y una descarga con `curl` no se interrumpe al cancelar el asistente: se espera a que termine el paso.
