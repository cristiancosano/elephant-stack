## Estado

Hecho lo que el plan asigna a P10 (00 §6, 04 §4.10). Archivos:

- `crates/elephant-core/src/needs.rs`
  - `project_needs(dir)`: lee `dir/.env` (sin escribir nunca, como mucho 1 MB) y devuelve los servicios y los motivos. Reglas de 04 §4.10:
    - `DB_CONNECTION` mysql/mariadb → `mysql`, pgsql → `postgresql`, con `DB_HOST` local;
    - `redis` en algún driver (`CACHE_STORE`, `QUEUE_CONNECTION`, `SESSION_DRIVER`, `BROADCAST_CONNECTION`, y los nombres antiguos `CACHE_DRIVER` y `BROADCAST_DRIVER`), con `REDIS_HOST` local; `REDIS_HOST` solo no cuenta;
    - `MAIL_MAILER` (o `MAIL_DRIVER`) `smtp`, `MAIL_HOST` local y `MAIL_PORT=1025` → `mailpit`.
    - «Local» es vacío, `127.0.0.1` o `localhost`. Si el host no es local, no se pide el servicio y queda un motivo («Sin redis: Redis está en …»).
    - El lector de `.env` entiende comentarios, `export`, comillas simples y dobles (también de varias líneas), comentarios al final de la línea e interpolación `${VAR}`. Si una clave se repite, gana la primera, como en Laravel.
    - Sin `.env` legible: `Needs` vacío con el motivo.
  - `start_project_services(dir)`:
    - toma el cerrojo de brew y aplica `Operation::TurnOn` (`brew services run`, o `start` si ya estaba registrado) solo a lo que no está en marcha; con algo arrancado, hace `stamp::touch("services")`;
    - una necesidad la cubre cualquier fórmula equivalente instalada: `mysql`, `mysql@X` o `mariadb` para mysql, y `postgresql@N` para postgresql. Si una ya está en marcha, no se arranca nada. Si no, elige la registrada al iniciar sesión, después por orden de fórmula y, por último, la versión más reciente;
    - devuelve los nombres de brew arrancados, vacío si no hacía falta nada. Da error si no hay `.env` legible, si falta algo por instalar («PostgreSQL no está instalado») o si brew falla. Aun así arranca todo lo que puede, y el mensaje dice qué arrancó.

## Para integración (P99)

1. **Comando `project_start_services(dir)` en `commands/core.rs`**:

   ```rust
   #[tauri::command]
   pub async fn project_start_services(app: AppHandle, dir: PathBuf) -> Result<Vec<String>, String> {
       tauri::async_runtime::spawn_blocking(move || crate::tray::start_project_services(&app, &dir))
           .await
           .map_err(|e| e.to_string())?
   }
   ```

   Regístralo en `lib.rs`, añádelo a la capability si hace falta, y en `ipc.ts`:

   ```ts
   export const projectStartServices = (dir: string) => invoke<string[]>("project_start_services", { dir });
   ```

   Después, en `Sites.svelte`, sustituye el acceso opcional (`ipc as { projectStartServices?: … }`) por un import normal y quita `import * as ipc`. Hasta entonces la opción del menú ⋯ no aparece, y `pnpm build` avisa de que el import es `undefined`.
2. **Mover la acción a `actions.rs`, si se prefiere.** `tray::start_project_services` repite el patrón privado `actions::tracked`, porque `actions.rs` no es de P10. Lo natural es dejarla en `actions.rs` y que el tray y el comando la llamen allí.
3. **`busy` y problemas con el id del proyecto como objetivo.** El tray (`problem_route`) ya lleva estos problemas a `#/sitios`. Hay dos sitios de `app.svelte.ts` y `Dashboard.svelte` que no lo saben:
   - la línea de estado muestra `${busy.target}: …`, que aquí sería el id hexadecimal del proyecto; convendría poner su nombre (`snapshot.projects`);
   - «Ver problema» del Dashboard manda a `#/servicios` todo lo que no es `php`; para un proyecto debería ir a `#/sitios`.
4. **Sin cambios de contrato exportado.** `Needs` sigue igual y no se exporta a TS. `TrayAction` es interno. No hay dependencias nuevas.
